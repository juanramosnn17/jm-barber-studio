# Decisiones Técnicas y de Producto · JM Barber Studio

| Fecha | Decisión | Por qué |
|---|---|---|
| 2026-11-14 | **Arquitectura de persistencia híbrida** (Supabase + Store reactivo en memoria `globalThis.__jm_store`) | Permite que la aplicación sea 100% funcional e interactiva de inmediato en local, demos o despliegues sin credenciales `.env.local`, sincronizando con PostgreSQL en Supabase cuando está configurado. |
| 2026-11-14 | **Next.js 16 App Router con Server Actions (`lib/actions.ts`) en lugar de un backend separado** | Simplifica el despliegue en un solo repositorio monolítico: las lecturas (`queries.ts`) y mutaciones (`actions.ts`) corren seguras en el servidor y actualizan la UI con `revalidatePath`. |
| 2026-11-14 | **Sistema de diseño "Sartorial Grooming System" en Tailwind CSS v4 (`@theme`)** | Centralizar los colores hexadecimales (crema `#FCF9F2`, negro `#000000`, bronce `#775A00`) y la escala tipográfica en `app/globals.css` garantiza consistencia visual y contraste WCAG AA/AAA en todas las vistas. |
| 2026-11-14 | **Control de acceso en dos capas (`middleware.ts` + validación en Server/Actions)** | Protege las rutas privadas (`/cliente`, `/admin`) desde el borde antes de renderizar y asegura que solo el rol `admin` pueda ver el módulo contable (`/admin/contabilidad/ganancias`) o registrar gastos, incluso si un `barbero` tiene acceso a `/admin`. |
| 2026-11-14 | **Cálculo automático de cobro al completar cita** | Cuando un admin o barbero marca una cita como `completada`, el sistema registra automáticamente su pago en efectivo (`payment_status = 'pagado'`), costo directo y comisión del barbero para alimentar el reporte de ganancias sin doble digitación. |
| 2026-11-14 | **Desactivación lógica de servicios (`is_active`) en lugar de borrado físico** | Evita romper el historial contable y las referencias (`service_id` con `ON DELETE RESTRICT`) de citas pasadas cuando un servicio sale de temporada. |
| 2026-11-14 | **[Supuesto SDD Inverso] Moneda, huso horario y mercado objetivo en Colombia (`COP`, `es-CO`, `+57`, `America/Bogota`)** | Se deduce de `lib/config.ts` y de los métodos de pago locales (`nequi_daviplata`) que el estudio opera en Colombia y maneja precios en pesos colombianos sin decimales. |
| 2026-11-14 | **[Supuesto SDD Inverso] Elección de la variante visual "Sartorial Grooming" (clara/crema) como referencia definitiva** | Se asume que durante la fase de diseño (Bloque 5) se descartaron variantes oscuras en favor de la paleta crema/carbón/dorado exportada desde Google Stitch por ofrecer mayor legibilidad diurna en dispositivos móviles. |
| 2026-11-14 | **[Supuesto SDD Inverso] Contraseña semilla `"123"` para cuentas de demostración en el store en memoria** | Se definió en `lib/data/store.ts` para facilitar las pruebas de evaluación de los roles `admin`, `barbero` y `cliente` sin requerir verificación de correo electrónico. |
| 2026-11-14 | **Publicación en GitHub (`juanramosnn17/jm-barber-studio`) y despliegue continuo en Vercel** | La copia local no tenía git; se creó un commit encima del historial existente del repo (sin forzar) y se desplegó en Vercel conectado al repo, de modo que cada push a `main` publica una versión nueva. URL: https://jm-barber-studio-delta.vercel.app |
| 2026-11-14 | **El backend se construye en Supabase (fase "Back · Supabase en la nube" de `docs/tareas.md`)** | El código ya está preparado (`isSupabaseConfigured()`), pero falta crear el proyecto, aplicar el esquema, configurar Auth y conectar las variables. Se separó en tareas pendientes para no dar por hecho algo que hoy corre en memoria. |
| 2026-11-14 | **El overbooking lo impide la base de datos (índice único parcial en `appointments (date, time)` para citas no canceladas)** | Al revisar el código se vio que `createAppointmentAction` solo valida contra el store en memoria antes de insertar en Supabase, y la tabla no tenía restricción de unicidad: dos clientes podrían tomar el mismo turno. La regla debe vivir en la base de datos, que es la única fuente compartida entre instancias serverless. |
| 2026-11-14 | **Disponibilidad vía función `get_booked_slots(date)` con `security definer`** | Con RLS cada cliente solo ve sus propias citas, así que no podría saber qué turnos tomaron otros. La función devuelve solo las horas ocupadas, sin nombres ni datos personales. |
| 2026-11-14 | **Contrato del backend en `docs/contratos/api.md`** | La guía ubica este documento como base de la Unidad 4. Fija entradas, salidas, tablas y rol permitido de cada acción antes de conectar Supabase. |
| 2026-11-14 | **Funciones `is_admin()` / `get_my_role()` con `security definer` para las políticas RLS** | Las políticas actuales consultan `profiles` desde las propias políticas de `profiles`, lo que en Postgres produce recursión infinita (`42P17`) y rompería casi todas las consultas. |
| 2026-11-14 | **El rol de un registro nuevo siempre es `cliente` (trigger `handle_new_user`)** | El trigger tomaba el rol de `raw_user_meta_data`, que envía el propio usuario; con la anon key pública cualquiera podía registrarse como `admin`. Ahora el rol solo lo cambia un administrador. |
| 2026-11-14 | **Un usuario no puede cambiar su propio rol** | La política de edición del propio perfil no protegía la columna `role`: un cliente podía hacerse admin. Se agregó `with check (role = get_my_role())`. |
| 2026-11-14 | **El barbero puede leer los perfiles** | La agenda de `/admin` (F3) muestra y busca por nombre de cliente, y el barbero tiene acceso a esa vista; sin este permiso vería las citas sin nombre. |
| 2026-11-14 | **Políticas con `drop policy if exists` y `with check`** | El script se puede volver a ejecutar sin errores, y las reglas de escritura validan también el registro resultante, no solo el existente. |
| 2026-11-14 | **Se borró el esquema antiguo del proyecto "Barberia JM" antes de aplicar `schema.sql`** | Tenía otro modelo (`full_name`, `barber_id`, `start_time`, `barber_schedules`) incompatible con el código. Estaba vacío salvo 3 servicios que ya vienen en la semilla nueva. El estudiante aprobó el borrado. |
| 2026-11-14 | **`handle_new_user()` sin permiso de ejecución por la API y sin la extensión `btree_gist`** | Lo recomendó el asesor de seguridad de Supabase: la función solo la usa el trigger, y la extensión era del esquema viejo. |
| 2026-11-14 | **[Riesgo aceptado] `get_my_role()` e `is_admin()` se pueden llamar por `/rest/v1/rpc`** | Las políticas RLS necesitan que `anon` y `authenticated` puedan ejecutarlas. Solo devuelven el rol del propio usuario. Si se quiere cerrar el aviso, la alternativa es moverlas a un esquema no expuesto. |
| 2026-11-14 | **El filtro de rutas (`proxy.ts`) toma el rol de la base de datos** | Al promover la primera cuenta a admin se vio que el filtro leía el rol de `user_metadata`, que el usuario puede modificar, y aceptaba la cookie demo `jm_user_session=user-admin` aun con Supabase conectado. Ambos permitían abrir pantallas de admin sin serlo. Con Supabase la única fuente del rol es `profiles` vía `get_my_role()`. |
| 2026-11-14 | **Con Supabase conectado, la app usa solo Supabase (sin mezclar el store ni los datos de ejemplo)** | El modo híbrido guardaba primero en memoria y luego "replicaba" en Supabase sin revisar el resultado, y las lecturas combinaban ambos lados: aparecían citas de ejemplo y se usaban ids locales (`usr-…`) contra columnas `uuid`. Ahora cada operación elige un solo modo: Supabase si está configurado y, si no, el store (modo demo intacto). |
| 2026-11-14 | **Cada escritura en Supabase confirma las filas afectadas (`.select("id")`)** | RLS no devuelve error cuando bloquea un `update`/`delete`: simplemente no afecta filas. Pedir las filas de vuelta permite responder `{ ok: false }` en ese caso. |
| 2026-11-14 | **Sin asignación de barbero/sillón en el MVP (un solo barbero)** | El estudiante indicó que hoy hay un solo barbero. La pantalla de asignación no existía; en vez de construirla, se sacó de la spec F3 y la tarea 3.17 quedó pospuesta. La acción y las columnas se conservan para retomarla. |
| 2026-11-14 | **El admin no puede eliminarse ni quitarse el rol de administrador** | Con un solo admin, hacerlo dejaría el estudio sin nadie que gestione la app. Lo bloquean `delete_user` en la base y `updateUserAction` en el servidor. |
| 2026-11-14 | **[Riesgo aceptado] Borrar un cliente borra también sus citas** | `appointments.client_id` es `on delete cascade`, así que al borrar un cliente desaparecen sus citas y su rastro en el reporte contable. Para el MVP se acepta; si se necesita conservar el historial, la alternativa es desactivar usuarios en vez de borrarlos. |
| 2026-11-14 | **[Riesgo aceptado] Cambiar el correo en `/admin/usuarios` no cambia el correo de inicio de sesión** | Solo se actualiza `profiles.email`; el correo de Supabase Auth sigue igual. Cambiarlo requiere la API de administración (`service_role`), que no se usa en el MVP. |
| 2026-11-14 | **El barbero solo usa la agenda; servicios, horarios, usuarios y contabilidad son del admin** | El estudiante preguntó si el barbero tenía las mismas funciones. El servidor ya le rechazaba esos cambios, pero el menú le mostraba las páginas y en Usuarios podía ver correos y teléfonos de todos. Ahora el menú y `proxy.ts` lo limitan a `/admin`. Reemplaza la decisión anterior de que "el barbero puede leer los perfiles". |
| 2026-11-14 | **Nombres de clientes para el barbero vía `get_client_names` en vez de leer `profiles`** | RLS no restringe columnas por rol. La función devuelve solo nombre y apellido, así la agenda del barbero muestra a quién atiende sin exponer datos de contacto. |
| 2026-11-14 | **Ajustes contables: anular (recomendado), editar, eliminar y ajustar pago** | El estudiante notó que no había forma de corregir la contabilidad. Anular conserva el gasto con su motivo y fecha (`void_reason`, `voided_at`) para auditoría; eliminar borra sin rastro y se reserva para datos de prueba, con confirmación dentro del comprobante (sin `confirm()` del navegador). El ajuste de pago solo aplica a citas completadas y valida que descuento + reembolso no superen el precio. |
| 2026-11-14 | **[Hallazgo] Las pruebas de `tests/accounting/` no se pueden ejecutar hoy** | Usan `node:test` con imports sin extensión y alias, y el proyecto no tiene ejecutor (`tsx`, `vitest`) ni script `test`. Fallan igual antes y después de los cambios. Queda para la Unidad 5 (pruebas). |
| 2026-11-14 | **Validar el rol dentro de cada Server Action y revisar el `error` de Supabase** | Las Server Actions se pueden invocar con un POST directo, así que proteger solo la página no basta; y hoy un fallo de Supabase se ignora, lo que muestra "guardado" sin haber guardado. |
| 2026-11-14 | **[Supuesto] Borrado de usuarios con la función `delete_user(id)` (`security definer`, solo admin)** | Permite borrar de `auth.users` sin poner la `service_role` key en el servidor de Vercel. Alternativa descartada: usar la API de administración de Supabase con esa key. |
| 2026-11-14 | **Migrar `middleware.ts` a `proxy.ts`** | Next.js 16 renombró la convención. El archivo actual funciona pero está obsoleto; la versión anterior del repositorio ya usaba `proxy.ts`. |
| 2026-11-14 | **[Supuesto] Capacidad de 1 cita por bloque horario** | Es lo que hace hoy el código (la validación compara solo fecha y hora). Aunque existe `barbers_count`, no se usa para permitir citas simultáneas; ampliarlo sería un cambio de spec posterior. |
| 2026-11-14 | **Reutilizar el proyecto Supabase "Barberia JM" (`us-west-2`) y desactivar la confirmación de correo en el MVP** | El estudiante prefirió reactivar el proyecto que ya tenía en lugar de crear uno en São Paulo (más cercano a Colombia); la latencia extra es aceptable para el MVP. Tenía un esquema antiguo vacío (0 filas, 0 usuarios) incompatible con el actual. Desactivar la confirmación permite cumplir el objetivo de "reservar en menos de 1 minuto" sin depender del envío de correos. |
| 2026-11-14 | **[Supuesto] Despliegue sin variables de Supabase** | Producción corre en modo demo (store en memoria) hasta configurar `NEXT_PUBLIC_SUPABASE_URL` y `NEXT_PUBLIC_SUPABASE_ANON_KEY` en Vercel; los datos del demo no persisten entre instancias serverless. |
