# Decisiones Técnicas y de Producto · JM Barber Studio

| Fecha | Decisión | Por qué |
|---|---|---|
| 2026-11-14 | **Arquitectura de persistencia híbrida** (Supabase + Store reactivo en memoria `globalThis.__jm_store`) | Permite que la aplicación sea 100% funcional e interactiva de inmediato en local, demos o despliegues sin credenciales `.env.local`, sincronizando con PostgreSQL en Supabase cuando está configurado. |
| 2026-11-14 | **Next.js 16 App Router con Server Actions (`lib/actions.ts`) en lugar de un backend separado** | Simplifica el despliegue en un solo repositorio monolítico: las lecturas (`queries.ts`) y mutaciones (`actions.ts`) corren seguras en el servidor y actualizan la UI con `revalidatePath`. |
| 2026-11-14 | **Sistema de diseño "Sartorial Grooming System" en Tailwind CSS v4 (`@theme`)** | Centralizar los colores hexadecimales (crema `#FCF9F2`, negro `#000000`, bronce `#775A00`) y la escala tipográfica en `app/globals.css` garantiza consistencia visual y contraste WCAG AA/AAA en todas las vistas. |
| 2026-11-14 | **Control de acceso en dos capas (`middleware.ts` + validación en Server/Actions)** | Protege las rutas privadas (`/cliente`, `/admin`) desde el borde antes de renderizar y asegura que solo el rol `admin` pueda ver el módulo contable (`/admin/contabilidad/ganancias`) o registrar gastos, incluso si un `barbero` tiene acceso a `/admin`. |
| 2026-11-14 | **Cálculo automático de cobro al completar cita** | Cuando un admin o barbero marca una cita como `completada`, el sistema registra automáticamente su pago en efectivo (`payment_status = 'pagado'`), costo directo y comisión del barbero para alimentar el reporte de ganancias sin doble digitación. |
| 2026-11-14 | **Desactivación lógica de servicios (`is_active`) en lugar de borrado físico** | Evita romper el historial contable y las referencias (`service_id` con `ON DELETE RESTRICT`) de citas pasadas cuando un servicio sale de temporada. |
| 2026-11-14 | **[Supuesto SDD Inverso] Moneda, huso horario y mercado objetivo en Colombia (`COP`, `es-CO`, `+57`, `America/Bogota`)** | Se deduce de `lib/config.ts` y de los métodos de pago locales (`nequi_daviplata`) que el estudio opera en Colombia y maneja precios en pesos colombianos sin decimales. |
| 2026-11-14 | **[Supuesto SDD Inverso] Elección de la variante visual "Sartorial Grooming" (clara/crema) como referencia definitiva** | Se asume que durante la fase de diseño (Bloque 5) se descartaron variantes oscuras en favor de la paleta crema/carbón/dorado exportada desde Google Stitch por ofrecer mayor legibilidad diurna en dispositivos móviles. |
| 2026-11-14 | **[Supuesto SDD Inverso] Contraseña semilla `"123"` para cuentas de demostración en el store en memoria** | Se definió en `lib/data/store.ts` para facilitar las pruebas de evaluación de los roles `admin`, `barbero` y `cliente` sin requerir verificación de correo electrónico. |
| 2026-11-14 | **Publicación en GitHub (`juanramosnn17/jm-barber-studio`) y despliegue continuo en Vercel** | La copia local no tenía git; se creó un commit encima del historial existente del repo (sin forzar) y se desplegó en Vercel conectado al repo, de modo que cada push a `main` publica una versión nueva. URL: https://jm-barber-studio-delta.vercel.app |
| 2026-11-14 | **El backend se construye en Supabase (fase "Back · Supabase en la nube" de `docs/tareas.md`)** | El código ya está preparado (`isSupabaseConfigured()`), pero falta crear el proyecto, aplicar el esquema, configurar Auth y conectar las variables. Se separó en tareas pendientes para no dar por hecho algo que hoy corre en memoria. |
| 2026-11-14 | **El overbooking lo impide la base de datos (índice único parcial en `appointments (date, time)` para citas no canceladas)** | Al revisar el código se vio que `createAppointmentAction` solo valida contra el store en memoria antes de insertar en Supabase, y la tabla no tenía restricción de unicidad: dos clientes podrían tomar el mismo turno. La regla debe vivir en la base de datos, que es la única fuente compartida entre instancias serverless. |
| 2026-11-14 | **Disponibilidad vía función `get_booked_slots(date)` con `security definer`** | Con RLS cada cliente solo ve sus propias citas, así que no podría saber qué turnos tomaron otros. La función devuelve solo las horas ocupadas, sin nombres ni datos personales. |
| 2026-11-14 | **Contrato del backend en `docs/contratos/api.md`** | La guía ubica este documento como base de la Unidad 4. Fija entradas, salidas, tablas y rol permitido de cada acción antes de conectar Supabase. |
| 2026-11-14 | **Funciones `is_admin()` / `current_role()` con `security definer` para las políticas RLS** | Las políticas actuales consultan `profiles` desde las propias políticas de `profiles`, lo que en Postgres produce recursión infinita (`42P17`) y rompería casi todas las consultas. |
| 2026-11-14 | **Validar el rol dentro de cada Server Action y revisar el `error` de Supabase** | Las Server Actions se pueden invocar con un POST directo, así que proteger solo la página no basta; y hoy un fallo de Supabase se ignora, lo que muestra "guardado" sin haber guardado. |
| 2026-11-14 | **[Supuesto] Borrado de usuarios con la función `delete_user(id)` (`security definer`, solo admin)** | Permite borrar de `auth.users` sin poner la `service_role` key en el servidor de Vercel. Alternativa descartada: usar la API de administración de Supabase con esa key. |
| 2026-11-14 | **Migrar `middleware.ts` a `proxy.ts`** | Next.js 16 renombró la convención. El archivo actual funciona pero está obsoleto; la versión anterior del repositorio ya usaba `proxy.ts`. |
| 2026-11-14 | **[Supuesto] Capacidad de 1 cita por bloque horario** | Es lo que hace hoy el código (la validación compara solo fecha y hora). Aunque existe `barbers_count`, no se usa para permitir citas simultáneas; ampliarlo sería un cambio de spec posterior. |
| 2026-11-14 | **[Supuesto] Región `sa-east-1` (São Paulo) y confirmación de correo desactivada en el MVP** | Es la región de Supabase más cercana a Colombia; desactivar la confirmación permite cumplir el objetivo de "reservar en menos de 1 minuto" sin depender del envío de correos. |
| 2026-11-14 | **[Supuesto] Despliegue sin variables de Supabase** | Producción corre en modo demo (store en memoria) hasta configurar `NEXT_PUBLIC_SUPABASE_URL` y `NEXT_PUBLIC_SUPABASE_ANON_KEY` en Vercel; los datos del demo no persisten entre instancias serverless. |
